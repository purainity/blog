# REDMI K90 Pro Max HyperOS 3.0.16 系统镜像网络端点静态分析

我用 AI 静态分析了 Redmi K90 Pro Max 的 HyperOS 3.0.16 系统镜像（为什么是这个版本？因为我手头的机器刚好是这个版本的，就直接拿它来分析了），试图找出系统中所有会发生真实外联行为的网络端点，并列举小米的云控、广告、反诈上传应用列表等行为的真相。

最终报告、中间所用的一些脚本、和 AI 的完整聊天记录都已公开：https://github.com/purainity/myron-hyperos-analysis  

注意：本项目完全由 AI 完成，可能有大量遗漏，仅供参考，准确性未知。

这个项目大概一周前就完成了，这段时间在想要不要、以及怎么把它放出来，最终决定在 8 月 16 日这个“特殊”的日子里以这种形式公开。

其实我早在七月初就有做这个项目的想法了，也尝试过几次，那时用的是 GPT-5.4，也许是因为模型降智，也许是因为我没有把规范和需求定明确，效果非常差，中途还因为磁盘空间满被迫终止、并发 jadx 导致 OOM 死机。

后来在 GPT-5.6 发布之后，我又重启了这个项目，主要用 gpt-5.6-terra，先制定明确的项目需求和操作规范、工作流程，然后推进的还算顺利。中途遇到偷懒和降智时临时切到 glm-5.2 用了一段时间。

当然意外也是有的，最大的一次就数有一回 apk 阶段的分析需求前后有变化，于是叫它回滚之前的工作。由于不是 git，所以它直接删目录，可能是它不知道正式报告目录中还有之前非 apk 阶段的已完成的报告，结果一起扬了。。。然后我急忙去问之前完成非 apk 阶段的那个 agent，并紧急 dd 导出整个磁盘，在 ext4 日志被覆盖的情况下找不到之前的文件，后来我灵机一动想到 OpenCode 的数据库里记录了所有的 AI 聊天记录，于是就叫另一个 agent 重放，成功恢复了之前的文件。

还有一个问题是永远补不完的遗漏。本来这次推进很顺利，但是在最后的复核阶段又发现了很多遗漏的条目。第一轮复核完成后我留了个心眼，又叫一个新的 agent 检查一遍，结果又发现一堆问题。。。后来换着模型相互核对，结果光复核阶段就检查了三遍多，花了大量时间。最终当前版本从头到尾用了大概半个月左右完成。而且根据之前的经验来看估计还有很多遗漏没有被发现，所以现在这个项目只能说有参考价值，没有任何准确性保证。

最后还是想吐槽一下我那可以算“恶劣”的工作条件：远古 CPU 跑 jadx 一个 apk 要几十分钟是正常现象、内存被 OpenCode 自身和 java 进程占满导致内核杀进程和直接系统卡死常有发生（所幸后来 AI 写了个 java 进程调度器自动调整后台 java 进程数量和资源限制，有效防止了 OOM 的情况、磁盘用完导致部分反编译产物不得不被打包到外部存储，结果在复核阶段不得不多次回迁、清理。
